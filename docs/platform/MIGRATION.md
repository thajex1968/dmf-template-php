# Migration Guide

Moving an existing DMF application off a committed path repository and onto the
development/release mode split.

**No breaking changes.** No application code is touched, no public API changes,
and local development keeps working exactly as it did — the same symlinked
`vendor/dmf/core`, the same immediate feedback when editing `../dmf-core`. What
changes is that the path repository stops being *committed*, so it can no longer
reach a build.

Budget 30–45 minutes.

---

## 1. Are you affected?

```bash
composer dmf:status
```

or, before the tooling exists:

```bash
grep -A3 '"repositories"' composer.json
```

You need this migration if `composer.json` contains:

```json
{ "type": "path", "url": "../dmf-core" }
```

---

## 2. Prerequisites

| | |
|---|---|
| `dmf/core` **≥ 1.1.0 tagged** | earlier tags predate `.gitattributes`, so V7 fails |
| A GitHub PAT with read access to `thajex1968/dmf-core` | the repo is private |
| A green test suite | so you can tell migration breakage from pre-existing breakage |

```bash
composer config --global --auth github-oauth.github.com ghp_xxxxxxxxxxxx
git checkout -b chore/release-pipeline-migration
composer test          # note the result before you start
```

---

## 3. Steps

### 3.1 Replace the path repository with a VCS repository

```diff
     "repositories": [
         {
-            "type": "path",
-            "url": "../dmf-core"
+            "type": "vcs",
+            "url": "https://github.com/thajex1968/dmf-core.git"
         }
     ],
     "require": {
-        "dmf/core": "@dev"
+        "dmf/core": "^1.1"
     },
+    "minimum-stability": "stable",
+    "prefer-stable": true,
```

`@dev` → `^1.1` is the substantive change: the application now depends on a
**released, tagged** library rather than whatever happens to be in a sibling
directory.

### 3.2 Add the mode-switcher scripts

Copy from this template:

```
scripts/dmf-mode.php
scripts/verify-release.php
scripts/build-release.php
```

and register them:

```json
"scripts": {
    "dmf:dev":     "@php scripts/dmf-mode.php dev",
    "dmf:release": "@php scripts/dmf-mode.php release",
    "dmf:status":  "@php scripts/dmf-mode.php status",
    "dmf:build":   "@php scripts/build-release.php",
    "dmf:verify":  "@php scripts/verify-release.php"
}
```

### 3.3 Declare the release payload

```json
"extra": {
    "dmf-release": {
        "output": "release",
        "include": [
            { "from": "public_html", "to": "." },
            { "from": "app",         "to": "app" },
            { "from": "VERSION",     "to": "VERSION" }
        ]
    }
}
```

`"to": "."` flattens a directory into the archive root. List exactly what the
application needs at runtime — the build fails if a declared path is missing,
so this list stays honest.

### 3.4 Ignore the development artifacts

```gitignore
# DMF development mode — generated by scripts/dmf-mode.php, never commit.
# Committing composer-dev.json would reintroduce a path repository into the
# tracked tree, which is the failure this migration removes.
composer-dev.json
composer-dev.lock

# Composer credentials for the private dmf/core repository.
auth.json

# Built release packages.
/release/*.zip
```

### 3.5 Start tracking `composer.lock`

This is the step most easily missed.

```diff
  # PHP / Composer
  /vendor/
- composer.lock
```

With a path repository the lock recorded `"dist": {"type": "path"}` — junk on
any other machine, which is why it was ignored. Over a VCS repository it records
a commit SHA and is reproducible, so it must be tracked.

```bash
composer update dmf/core --with-dependencies
git add -f composer.lock
```

Confirm it is now sane:

```bash
grep -A3 '"name": "dmf/core"' composer.lock
#   "version": "v1.1.0",
#   "dist": { "type": "zip", "url": "https://api.github.com/repos/..." }
```

`"type": "zip"` — not `"path"`.

### 3.6 Update CI

Jobs no longer need a sibling checkout of `dmf-core`. Replace:

```yaml
- uses: actions/checkout@v4
  with: { path: my-app }
- uses: actions/checkout@v4          # ← delete this
  with:
    repository: thajex1968/dmf-core  # ← and this
    path: dmf-core                   # ← and this
```

with a single checkout plus authentication:

```yaml
- uses: actions/checkout@v4

- name: Install dependencies
  env:
    COMPOSER_AUTH: '{"github-oauth":{"github.com":"${{ secrets.DMF_CORE_TOKEN }}"}}'
  run: composer install --no-interaction --prefer-dist --optimize-autoloader
```

Every `working-directory:` and nested-path workaround that existed only to make
`../dmf-core` resolve can go. Cache keys can go back to
`hashFiles('composer.lock')`, which is now a real, tracked file.

Copy `build.yml`, `verify-release.yml` and `release.yml` from this template.

### 3.7 Retire the old build script

If the project has a `build-release.sh`/`.ps1` that copies a junction into a
real directory:

```bash
# Delete this kind of thing — it is the workaround, not the fix.
if [[ -L "$CORE_LINK" ]]; then
  rm "$CORE_LINK"
  cp -r "$CORE_TARGET" "$CORE_LINK"
  for _d in .git tests docs .github vendor; do rm -rf "$CORE_LINK/$_d"; done
fi
```

`scripts/build-release.php` replaces it. The stripping loop is now
`.gitattributes` `export-ignore` in `dmf-core`, applied by `git archive` when
Composer fetches the dist — done once for every consumer instead of
re-implemented in every project's build script.

Keep the old script until §4 passes, then delete it in the same PR.

## 4. Verify the migration

```bash
# 1. Release mode installs from Git as real files
composer dmf:release
composer dmf:status
#    vendor/dmf/core:  real directory (62 files)
#    Packageable:      yes

# 2. Development mode still gives immediate feedback
composer dmf:dev
composer dmf:status
#    vendor/dmf/core:  symlink → …/dmf-core
#    …edit ../dmf-core/src/… and confirm the app sees it

# 3. Tests pass in both modes
composer test

# 4. A build from a DEV-mode tree still produces a correct package
#    (build-release.php stages from the committed manifest, so mode is irrelevant)
composer dmf:build
#    → PASS — artifact is safe to deploy.

# 5. Back to release mode before committing
composer dmf:release
```

Step 4 is the one worth doing deliberately: it proves the build no longer
depends on the developer remembering to switch modes first.

---

## 5. Acceptance criteria

| | Criterion | Check |
|---|---|---|
| Dev | `composer dmf:dev` → `vendor/dmf/core` is a symlink | `composer dmf:status` |
| Dev | Editing `../dmf-core` is visible with no rebuild | edit and reload |
| Release | `composer install` → `vendor/dmf/core` is real files | `composer dmf:status` |
| Release | No `type: path` in any committed manifest | `grep -r '"path"' composer.json` |
| Release | `composer.lock` tracked, `dist.type` is `zip` | `git ls-files composer.lock` |
| Package | ZIP contains no symlink | `composer dmf:verify -- --zip …` |
| Package | `vendor/dmf/core/src/Security/Sanitizer.php` present | same |
| Deploy | Extract on DirectAdmin → works, no manual copy | §6 |

---

## 6. First deployment after migrating

Treat it as a normal deployment ([`DIRECTADMIN_GUIDE.md`](DIRECTADMIN_GUIDE.md))
with one extra check: after extracting, open
`vendor/dmf/core/src/Security/` in the File Manager and confirm real files are
there. That directory being empty was the original bug; seeing four `.php` files
is the migration working.

---

## 7. Rollback

The migration touches only packaging, so reverting is a plain revert:

```bash
git revert <migration-commit>
composer install
```

Nothing about the deployed application changes, so no rollback is needed on the
server side.

---

## 8. Common problems

| Problem | Cause | Fix |
|---|---|---|
| `Could not find package dmf/core in any version` | private repo, no token | `composer config --global --auth github-oauth.github.com <PAT>` — GitHub 404s unauthenticated clients, so this looks like a missing package |
| `dmf/core ^1.1 could not be resolved` | no `1.x` tag yet | tag `dmf-core` v1.1.0 first |
| V7 fails: dev files under `vendor/dmf/core` | tag predates `.gitattributes` | require `^1.1` |
| `composer dmf:dev` cannot find `../dmf-core` | no sibling checkout | clone it beside the project |
| CI cannot find `dmf/core` | `DMF_CORE_TOKEN` not set | add the Actions secret |
| Lock still shows `"type": "path"` | lock not regenerated | `composer update dmf/core` |
| `composer-dev.json` appears in `git status` | `.gitignore` not updated | §3.4 — it must never be committed |

## 9. Migrating a *new* project

Start from this template. It is already in this shape — clone, run
`composer install`, and you are in release mode with the whole pipeline wired
